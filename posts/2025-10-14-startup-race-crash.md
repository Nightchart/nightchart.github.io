上一篇写的死锁是"程序站着不动"，这篇的剧本相反：**程序动得很快，然后死给你看**。而且只死百分之一的情况——测试环境跑一百次都正常，客户那里隔三差五崩一次。这类问题最消耗心智的地方不是修复，是**你根本无法稳定复现它**。

老规矩，脱敏讲思路，不提具体产品。

## 现象：三种"随机"

崩溃报告凑齐之后，发现它有三种出场方式：

- **崩溃栈乱指**：栈回溯跳到不可能的地址，或者直接是一串问号
- **空指针异常**：某个成员指针是 nullptr，但代码里明明"初始化过了"
- **数据莫名损坏**：某个配置对象偶发性内容不对，后续逻辑拿着错数据越走越远

三种现象共享同一个特征：**都发生在启动阶段**。程序跑起来之后稳如泰山。

经验判断："栈乱指 + 启动期 + 低概率"，八成不是内存越界，而是**数据竞争**——两个线程在没有同步的情况下碰同一份内存。栈乱指的典型成因就是：读到一半的对象被另一个线程改了布局（vtable 指针还没写好，虚函数调用就飞了）。

## 缩小包围圈：让时序现形

低概率竞态的定位，靠"盯"是盯不出来的。两个手段比肉眼有效：

**一是放大。** 竞态的本质是两个线程的执行顺序恰好在悬崖边。那就人为改变时序：在嫌疑路径上加毫秒级延迟（哪怕临时硬编码 sleep）、提高并发度、用最慢的机器跑。延迟注入这招看着土，但对"启动期时序依赖"有奇效——**你把隐藏的依赖关系变成了必现的崩溃**，问题就已经解决一半了。

**二是上工具。** ThreadSanitizer（TSAN）对数据竞争是精确制导的。编译一份 TSAN 版本跑压测，它会直接报出"哪两行代码、哪两个线程、哪次内存访问构成竞争"。唯一的前提是你能拿到源码构建——排查黑盒发布包时没这个待遇，这也是为什么我建议排查从延迟注入开始、TSAN 作为确认手段。

包夹之下，案发现场很快锁定了。

## 根因：一个"应该已经好了"的指针

脱敏后的问题模式长这样：

```cpp
class ConfigManager {
public:
    static ConfigManager& Instance();
    void Load();                      // 耗时：读文件、解析
    const Rule* FindRule(int id) {
        return rules_ ? rules_->lookup(id) : nullptr;   // ① 先检查后使用
    }
private:
    RuleTable* rules_ = nullptr;      // ② 声明处置空，这点是对的
};
```

单看每一行都没毛病：指针在声明处初始化为 nullptr（②），使用前有判空（①）。问题出在**时序假设**上：

线程 A（业务初始化流程）在启动早期调用了 `Load()`，`Load()` 内部先置了某个中间状态，然后去做耗时的文件解析；线程 B（一个更早被拉起的消息处理线程）几乎同时调用了 `FindRule()`。两个线程对 `rules_` 这一个指针的写入和读取之间，**没有任何同步**。

C++ 标准对这种情况的措辞是"数据竞争，行为未定义"。实践中你会看到编译器优化带来的各种幻术：读线程可能永远读不到写线程的新值（值被缓存在寄存器里）、可能读到"中间状态"、也可能因为指令重排读到完全出乎意料的顺序。

更隐蔽的是第二层：就算把 `rules_` 的读写改成原子，**"指针非空"不等于"对象已构造完成"**。写线程先发布指针、后初始化指向的对象，读线程拿着非空指针访问半成品——判空形同虚设。这就是经典的"先检查后使用"（check-then-act）陷阱：**检查的那一瞬间为真，不代表使用的那一瞬间仍然为真。**

## 修复：三层收敛

**第一层：时序显式化。** "谁必须在谁之前完成"不该靠启动顺序碰巧，应该有明确的依赖表达。修复后采用两阶段：构造只做无依赖的成员初始化，`Load()` 由明确的初始化流程在依赖就绪后调用；在此之前，所有查询方拿到的是明确的"未就绪"语义（空结果），而不是碰运气的半个对象。

**第二层：正确的同步原语。** 确实需要"延迟初始化 + 多线程安全"的地方，别手写 double-checked locking——C++11 之后有现成的正解：

```cpp
// 懒加载 + 线程安全，两个姿势任选
static const RuleTable& GetTable() {
    static const RuleTable table = BuildTable();   // 姿势一：Meyers 单例，
                                                   // C++11 保证初始化线程安全
}

// 姿势二：std::call_once，适合初始化动作复杂、需要显式控制的场景
std::once_flag flag_;
std::unique_ptr<RuleTable> table_;

const RuleTable& Table() {
    std::call_once(flag_, [this] { table_ = std::make_unique<RuleTable>(LoadRaw()); });
    return *table_;
}
```

**第三层：把"裸指针 + 手工判空"换成类型系统兜底。** 成员指针一律 `unique_ptr`，所有权清晰；未初始化就是空，判空逻辑集中在一处。散落在各处的裸指针判空，每一处都是一次时序赌注。

## 防复发清单

启动期竞态的阴险之处：修复后测试全绿，半年后有人加了条新启动路径，雷又响了。所以 review 时对照这张单：

- 每个指针成员，**声明处即初始化**（nullptr 或直接构造）；能用 `unique_ptr` 不用裸指针
- 任何"先检查后使用"的组合（判空→解引用、存在→读取、就绪→调用），问一句：**两步之间，另一个线程会插进来吗？**
- "指针非空"不等于"对象就绪"——懒加载对象必须用 Meyers 单例或 `call_once`，禁止手工 DCLP
- 启动流程画一张时序图：哪些对象被哪些线程在什么时机访问？答不上来，就是雷
- 竞态修复必须配复现手段：延迟注入脚本 + TSAN 构建进 CI，否则修复无法自证

## 小结

- **现象识别**：启动期 + 低概率 + 栈乱指/空指针/数据损坏三选一 → 优先怀疑数据竞争
- **定位手法**：延迟注入把隐藏时序变成必现，TSAN 做精确确认
- **根因模式**："先检查后使用"的时序假设 + 非原子发布
- **修复方向**：时序显式化（两阶段初始化）、`call_once`/Meyers 单例替代手写 DCLP、`unique_ptr` 收敛所有权
