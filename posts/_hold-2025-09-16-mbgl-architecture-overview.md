从这篇开始，系列进入代码世界。前几篇我们聊的是标准：数据怎么存（S-57）、显示怎么定（S-52）。但标准只规定"输入和输出"，中间那台把数据变成像素的机器——渲染引擎——是每个开发者真正朝夕相处的部分。

我们选 MapLibre Native（社区里习惯叫 **mbgl**）：C++ 写就的地图渲染内核，Android / iOS / Qt 桌面端共享同一套核心；它的孪生兄弟 MapLibre GL JS 负责浏览器端。选它有三个理由：工业级（Fork 自 Mapbox GL Native，久经生产考验）、完全开源（BSD-2）、且它的许多设计决策对任何做图形/GIS 引擎的人都有参考价值。

这篇是走读的开篇，目标是建立一张**架构地图**：线程怎么分、瓦片怎么调、一帧怎么画。有了这张图，后面读具体代码才不会迷路。

## 全景：一帧的生命周期

先给结论。用户手指在地图上一滑，到屏幕上出现新画面，中间发生的事可以概括成四步：

1. **平台层**捕获手势，更新相机参数（经纬度、缩放、角度）
2. **地图线程**根据新相机状态算出"应该有哪些瓦片"，缺的就地发起加载
3. **工作线程**们并行解析下载回来的瓦片数据，生成几何
4. **渲染器**把已有的几何按图层顺序绘制成帧

四个步骤分属不同的执行流，靠消息驱动串起来。下面逐个拆。

## 线程模型：四类执行流，没有一把大锁

mbgl 给人的第一印象是"线程好多"，第二印象才是"线程虽多，代码里却几乎见不到锁"。这两件事是同一个设计的结果。

**四类执行流：**

- **平台线程**：宿主 App 的 UI 线程。mbgl 不拥有它，只是接入——手势、生命周期回调从这里进来。
- **地图线程**：Map 对象的家。相机状态、图层增删、查询（queryRenderedFeatures）这些"地图业务逻辑"都在这里跑，和 UI 线程隔离，界面永不因地图逻辑卡顿。
- **工作线程池**：瓦片解析的重活——矢量数据解码、几何三角化、要素过滤——全部卸到这里。解析一个瓦片可能几毫秒到几十毫秒，绝不占用地图线程。
- **资源线程**：网络请求与缓存（FileSource 体系），下载、重试、ETag 校验都在这条线上。

**把它们粘起来的是 Actor 模式。** 这是 mbgl 最值得学的一个设计：每个长寿对象（Map、Renderer、FileSource、每个 TileWorker）都是一个 Actor——它拥有自己的信箱（Mailbox），其他线程想让它干活，不调用它的方法、不加锁，而是往它信箱里投一条消息。对象在自己的线程上按序消费消息，**内部代码因此完全不需要考虑并发**。

对 C++ 工程师的启发很直接：跨线程 bug 的根源是"共享可变状态"，mbgl 用消息传递把共享面压到了最小。你调试它的时候会发现每个线程都有清晰的名字，attach 上去一眼分清谁是谁——这是工程素养，抄作业不丢人。

**再往下是一层 RunLoop 抽象。** 地图线程不可能凭空转起来，它需要宿主平台的事件循环：Android 上是 Looper，iOS 上是 dispatch queue，Qt 上是事件循环。mbgl 用一个 RunLoop 接口把这些差异抹平，同一个 C++ 核心才算真正跨了平台。

## 瓦片调度：一台永不停歇的优先级机器

相机一动，需要哪些瓦片就变了。调度器的日常是回答三个问题：

**要哪些？** 相机状态投影到金字塔上，算出一组"理想瓦片 ID"（ideal tiles）——视野覆盖的行列号，按到屏幕中心的距离排优先级，中间的先加载。

**加载到哪了？** 每个瓦片是一台小状态机：排队 → 数据到达 → 解析完成 → 可渲染（或出错）。渲染器每帧检查状态，只画"可渲染"的。

**没加载完怎么兜底？** 关键设计是**父瓦片过度缩放（overscale）**：子瓦片没就绪时，先用低层级的父瓦片拉伸显示——用户看到的是略糊但完整的图，而不是一片空白。这个"宁糊勿空"的策略是地图体验的基石，几乎所有的主流引擎都有对应实现。

此外还有两件不起眼但决定体验的小事：离开视野或优先级太低的请求会被**取消**（省流量省算力）；退出视野的瓦片不立刻销毁，进一个 **LRU 缓存**——用户滑回来时瞬间恢复，内存超限时才按最近最少使用淘汰。

## 渲染管线：每帧都在"重新解释"样式

瓦片就绪后，渲染器的工作是把它们按样式规则画出来。有几个概念值得单独说：

**Bucket（桶）。** 解析瓦片时，每个图层会把自己的几何整理成一份"桶"：顶点缓冲、索引、按要素分组的元信息。解析是一次性的重活，绘制是每帧的轻活——这个分离就是工作线程存在的意义。

**绘制顺序 = 样式顺序，符号例外。** 图层按样式文件里的顺序画，但文字和图标（symbol 图层）永远最后画，而且有自己的**跨瓦片索引**：同一个地名在相邻瓦片重复出现时，跨瓦片去重保证缩放过程中标注不跳变。地图标注稳定性是个被低估的难题，mbgl 的 cross-tile 机制值得单独写一篇。

**文字是 SDF。** 字形以有向距离场（SDF）形式进图集，运行时按需缩放着色——所以地图文字放大不糊、旋转不锯齿，还免费获得碰撞检测、避让、屏幕对齐这一整套标注能力。

**动画 = 每帧重算绘制属性。** 缩放过渡时线宽、颜色都在插值，mbgl 不预烘任何中间结果，每帧按当前缩放级别重新求值绘制属性。还记得第一篇说的"安全等深线是船员的设置，颜色不能烘死在瓦片里"吗？mbgl 的架构天然站在这一边——这正是我们选它做海图渲染底座的原因之一。

## 读码路线

给想下源码的朋友一条路径（仓库 maplibre/maplibre-native）：

1. `include/mbgl/map` + `src/mbgl/map`——从 Map 和 Transform 入手，看相机状态怎么驱动一切
2. `src/mbgl/tile`——瓦片状态机和 TileWorker，观察解析怎么被卸载到工作线程
3. `src/mbgl/actor`——Actor / Mailbox 模板实现，百来行代码，是全文最值得抄的设计
4. `src/mbgl/renderer`——渲染编排，看图层怎么分组、一帧怎么画出来

读码心法：mbgl 的消息是异步的，断点单步会"跟丢"——顺着 Actor 的消息类型读，比顺着调用栈读更符合它的真实结构。

## 小结

- 四类执行流（平台 / 地图 / 工作池 / 资源），Actor + Mailbox 消息驱动，业务代码无锁
- 瓦片调度三问：要哪些（ideal tiles）、到哪了（状态机）、怎么兜底（父瓦片 overscale + LRU 缓存 + 取消）
- 渲染管线：Bucket 分离重活与轻活，符号层最后画 + 跨瓦片去重，SDF 文字，动画靠每帧重算
- 对海图开发的启示：这套架构对"船员参数运行时生效"是天然友好的
